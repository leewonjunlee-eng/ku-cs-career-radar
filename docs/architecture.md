# 공통 설계·인증·배포

[프로젝트 소개](../README.md) · [구현 순서](implementation-plan.md)

> 구현 전 설계다. 모든 기능에 적용되는 인증·보안·무결성·배포 기준의 단일 문서다. 기능 상세는 [공고](features/opportunities.md), [후기](features/reviews.md), [팀](features/teams.md)을 참조한다.

## 기술 스택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 웹 | Next.js + TypeScript + Tailwind CSS | UI와 API Route를 빠르게 만들고 Vercel 배포가 간편함 |
| DB/인증 | Supabase (PostgreSQL + Auth) | 공고 데이터, 북마크, 로그인 기능을 한 서비스에서 빠르게 구현 |
| 배포 | Vercel | GitHub 연동 및 `*.vercel.app` 공개 URL 생성이 빠름 |
| 데이터 수집 (추가 목표) | 공개 출처별 수집 스크립트 → Supabase | 먼저 출처 1곳에서 1회 실행 결과 저장, 실패해도 기존 데이터 유지 |
| 초기 데이터 | Supabase Seed | 원문을 확인한 실제 공고와 명시적으로 표시한 예시 후기를 구분 |

Next.js App Router를 사용하며 선택 버전과 lockfile을 고정한다. Supabase Auth만 브라우저에서 직접 사용하고 모든 앱 데이터는 서버 API를 거친다.

## 로그인과 권한

- 공고·후기·공개 팀 모집글 열람은 로그인 없이 가능
- 저장, 후기 작성, 팀 생성, 참여 요청 시 Supabase Auth 로그인 필요
- 작성자는 자신의 후기만 수정·삭제하고, 팀장은 자신의 팀 모집 정보와 참여 요청만 관리
- 앱 테이블은 RLS 활성화와 직접 접근 권한 회수로 보호하고, Next.js API에서는 검증된 사용자에 대한 권한 검사를 수행. 서버의 service-role 요청은 RLS를 우회하므로 RLS가 서버 코드의 누락까지 막아준다고 가정하지 않음
- 익명 후기는 공개 화면과 응답에서 작성자를 숨기되 내부 작성자 식별은 유지. 공개 조회에서 `author_id`가 노출되지 않게 설계
- 고려대 학생 중심으로 시작하되 학교 인증은 후속 기능이며, 이메일 로그인만으로 학교 인증 완료라고 표시하지 않음

### 공개 조회와 비공개 데이터 분리

- RLS는 행 접근 제어이므로 같은 행의 특정 컬럼을 숨기는 용도로 사용하지 않는다.
- `public_reviews` 뷰는 공개할 컬럼을 명시적으로 선택하고 `author_id`를 제외하며 예시 표시용 `is_demo`를 포함한다. 표시 이름은 익명일 때 `익명`, 그 외에는 닉네임만 제공한다.
- `public_teams` 뷰도 공개 모집 정보와 멤버 수 집계 `member_count`만 선택하고 `owner_id`는 제외한다. 연락 링크는 `teams`에서 제거하고 별도 `team_contacts`에 저장한다.
- MVP에서는 인증만 Supabase Auth를 직접 사용하고, 모든 앱 데이터 조회·쓰기는 Next.js API를 거친다. 서버의 공개 후기·팀 조회는 위 두 뷰를 사용한다. `subjects`, `opportunities`, `profiles`, `bookmarks`, `reviews`, `teams`, `team_contacts`, `team_members`, `team_requests` 및 두 뷰의 직접 Data API 권한은 `PUBLIC`/`anon`/`authenticated`에서 회수한다. 브라우저 코드에서 뷰만 쓰도록 하는 관례에 의존하지 않는다.
- 두 뷰는 `security_invoker = true`로 만들고 서버의 `service_role`에 뷰 및 필요한 원본 테이블 권한을 명시적으로 부여한다. service-role 클라이언트는 사용자 세션용 클라이언트와 분리하고 서버 전용 모듈에 둔다. 서버용 키는 브라우저·로그·저장소에 전달하지 않는다. 이 역할은 RLS를 우회하므로 사용자별 작업은 서버에서 세션을 검증하고 소유권·팀원 여부를 확인한다.
- 앱 DB 함수의 `EXECUTE`도 `PUBLIC`/`anon`/`authenticated`에서 회수하고 필요한 함수만 `service_role`에 부여한다. 새 테이블·함수의 기본 권한도 마이그레이션 생성 역할 기준으로 제한한다. 테이블 RLS만으로 RPC 호출을 차단했다고 가정하지 않는다.
- 앱 테이블에는 사용자 직접 접근을 허용하는 RLS 정책을 만들지 않고 기본 거부를 유지한다. 권한 회수·RLS·서버용 명시적 GRANT를 같은 마이그레이션에 포함한다.
- 팀 변경 RPC는 `SECURITY INVOKER`를 기본으로 하고 서버가 검증한 사용자 ID를 인자로 전달하여 함수 안에서 팀장·요청자 권한을 다시 확인한다. 클라이언트가 보낸 사용자 ID나 service-role 호출의 `auth.uid()`로 사용자를 판단하지 않는다.
- 내 후기 관리 API는 검증된 사용자 ID로 필터링한다. 팀 연락 조회 API는 팀장 또는 수락된 팀원인지 확인한 후에만 링크를 반환하며, 개인 응답을 공용 캐시에 저장하지 않는다.
- 공개 후기와 팀 조회 응답은 허용된 필드만 반환한다. 쓰기 API도 클라이언트가 보낸 작성자 ID를 신뢰하지 않는다.

| 데이터·작업 | Next.js API에서 허용하는 범위 |
| --- | --- |
| 공고·대상·공개 후기·팀 모집 | 비로그인 조회 가능. 공개 응답에 사용자 UUID, 연락 링크, 요청 메시지, 멤버 명단을 포함하지 않음 |
| 공고·대상 등록 및 갱신 | 개발자의 seed/관리 스크립트만 사용. 일반 사용자용 쓰기 API 없음 |
| 프로필·북마크 | 검증된 본인의 조회·수정만 허용. 공개 닉네임은 후기·팀 응답에 필요한 경우에만 제공 |
| 후기 | 로그인 사용자 작성, 본인만 수정·삭제. `author_id`와 `is_demo`는 일반 사용자가 지정·변경 불가 |
| 팀·연락 정보 | 로그인 사용자 생성, 팀장만 모집 정보·연락 링크 수정. 연락 조회는 팀장·수락된 팀원만 허용 |
| 요청·멤버 | 요청자는 자신의 요청 조회·취소, 팀장은 자기 팀 요청 조회·수락·거절. 멤버 등록은 팀 생성·수락 RPC만 수행 |

### API 최소 안전 규칙

- 서버에서 `getClaims()` 또는 `getUser()`로 토큰을 검증한 뒤 권한을 판단한다. `getSession()`이 반환한 사용자 객체나 클라이언트 입력만 신뢰하지 않는다.
- 쿠키 기반 쓰기 API는 GET으로 상태를 변경하지 않으며, 허용된 동일 출처의 `Origin`을 검사하여 교차 사이트 요청을 거부한다. 인증 실패·권한 거부·상태 충돌·입력 오류를 구분해서 응답한다.
- 내 활동, 연락 정보, 세션 갱신 응답은 `Cache-Control: private, no-store`로 공용 캐싱을 금지한다. 공개 응답에도 사용자별 필드나 세션 쿠키가 섞이지 않게 한다.
- 서버에서 필수 값, 문자열 길이, enum, 배열 크기, 유형별 `details` 허용 키와 값 타입을 검증한다. 후기·소개·요청 메시지는 일반 텍스트로 렌더링하고 임의 HTML을 실행하지 않는다.
- 원문·연락 링크는 `http`/`https` URL만 허용한다. 사용자 입력 URL을 서버가 임의로 가져오는 미리보기 기능은 MVP에 두지 않는다.
- 목록 API는 페이지 크기 상한과 안정적인 정렬 기준을 두고, 로딩·빈 결과·실패·중복 제출 상태를 화면에서 구분한다.

### 인증과 발표 계정

- 이메일·비밀번호 로그인을 사용한다. 공개 서비스의 이메일 확인은 유지하고, 발표용으로 미리 확인 완료한 두 계정을 준비한다. 발표 도중 신규 가입이나 메일 수신에 의존하지 않는다.
- Magic Link 역시 메일 확인이 필요하므로 발표용 해결책으로 삼지 않는다.
- `auth.users` INSERT 후 `profiles`를 생성하는 트리거를 둔다. 닉네임이 없으면 이메일 대신 기본 닉네임을 넣으며, 기존 계정의 누락 프로필은 보충한다.
- 가입 트리거 함수는 필요한 INSERT 권한을 가진 소유자의 `SECURITY DEFINER`, 고정된 `search_path`, 명시적 테이블 경로를 사용하고 클라이언트 실행 권한은 회수한다. 프로필 생성·보충은 `ON CONFLICT (id) DO NOTHING`으로 기존 프로필을 덮어쓰지 않는다. 트리거 실패는 가입 실패로 이어질 수 있으므로 신규 가입과 프로필 생성까지 확인한다.
- 공개 배포 전 Supabase Site URL·허용 리다이렉트 URL과 가입 확인 콜백을 설정하고 실제 확인 메일 흐름을 검증한다. 발표 계정의 비밀번호는 저장소·seed·공개 화면에 넣지 않는다.

## 공통 무결성과 삭제 정책

- 각 엔터티 ID에는 기본 키를 두고 사용자 참조는 `profiles(id)`, 공고·팀·대상 참조는 해당 테이블의 외래 키로 연결한다. `bookmarks`와 `team_members`는 명시한 두 컬럼을 복합 기본 키로 사용한다.
- 필수 필드는 NOT NULL, 상태·유형은 enum 또는 CHECK, 정원·경험 연도 등은 합의한 범위 CHECK를 둔다. 익명·예시 여부는 NOT NULL과 명시적 기본값을 사용한다. 공백만 있는 필수 문자열도 거부한다.
- 공고·대상은 MVP에서 물리 삭제하지 않는다. 후기·팀의 참조는 RESTRICT/NO ACTION으로 보존하며 공고 마감은 삭제로 처리하지 않는다. 계정 삭제 UI도 후속 범위로 둔다. 운영상 개인정보 삭제 요청은 공개된 문의 경로를 통해 개발자가 관련 작성물·소유 팀을 확인하고 처리한다.

## 공통 출시 검증

- 새로고침 후에도 작성한 후기, 팀, 참여 요청, 저장 목록이 유지된다.
- 비로그인 역할과 로그인 사용자 토큰 각각으로 앱 원본 테이블·뷰 직접 조회/쓰기 및 팀 RPC 직접 호출을 시도해 모두 거부되는지 확인한다. UI 버튼 숨김으로 검증을 대신하지 않는다. Next.js API에도 타인 ID·팀 ID와 위조된 작성자/행위자 ID를 보내 권한 우회가 안 되는지 확인한다.
- 저장은 같은 공고에 반복해도 중복되지 않고 취소 후 목록에서 사라진다. 후기 수정·삭제, 닉네임 변경 및 팀장 모집 정보·연락 링크 변경이 재조회에 반영된다.
- `is_demo`를 일반 사용자가 바꿀 수 없으며, 예시 보기의 배지와 일반 조회·집계에서의 예시 제외를 확인한다. 개인 응답과 세션 쿠키가 계정 사이에 캐시로 섞이지 않는다.
- 신규 가입 시 프로필이 자동 생성되고, 발표용 두 계정은 이메일 수신 없이 로그인할 수 있다.
- 공개 URL에서 로그인 복귀, 직접 상세 URL 접근, 모바일 표시를 확인한다.

기능별 판정은 각 문서의 완료 기준·테스트를 함께 확인한다. 아래 검증 명령은 앞으로 정의할 계약이며 현재 실행 가능한 코드나 테스트 성공 기록이 아니다.

각 단계는 작은 변경으로 나누어 `실패 사례 작성 → 실패 확인 → 최소 구현 → 통과 확인 → 관련 회귀 검증 → diff 리뷰` 순서로 진행한다. DB 권한과 동시성은 mock만으로 검증하지 않고 실제 별도 DB에서 확인한다. UI 전체 E2E 프레임워크 도입은 필수가 아니며 핵심 흐름 수동 리허설로 시작할 수 있다.

1단계에서 다음 package.json 스크립트를 정의한다. 지금 이 명령이 존재하거나 통과했다는 뜻은 아니다.

| 명령 | 정의할 동작 | 통과 기준 |
| --- | --- | --- |
| `npm run typecheck` | `tsc --noEmit` | 타입 오류 없음 |
| `npm run test:unit` | `vitest run tests/unit` | 지정 단위 테스트 성공 |
| `npm run test:integration` | `vitest run tests/integration` | 별도 테스트 DB 대상 통합 테스트 성공 |
| `npm run build` | `next build` | 프로덕션 빌드 성공 |
| `npm run dev` | `next dev` | 로컬 핵심 흐름 확인 가능 |

대상별 확인 예: `npm run test:integration -- tests/integration/team-transactions.test.ts`. 통합 테스트 시작 시 대상이 테스트 DB인지 검사하고 운영 DB이면 중단한다. 비밀값은 출력하지 않는다. 테스트용 데이터와 사용자를 격리하고 종료 후 정리한다.

커밋은 단계별 검증 후 해당 변경만 포함하도록 한다. 원격 push·배포는 실제 실행 시 승인된 저장소/프로젝트에 한해서 수행한다.

## 발표 준비와 리허설

- 발표 두 계정은 일반 창과 별도 브라우저 프로필/시크릿 창에서 각각 운용한다. 동시성 검증용으로는 팀장 외에 서로 다른 두 지원자 계정을 별도로 준비한다.
- 테스트용 마감 경계·실패 데이터는 로컬/별도 테스트 DB에서 사용하고 실제 공고로 배포하지 않는다. 발표에 쓸 열린 실제 공고가 없으면 콘텐츠 준비 미완료로 알리고 해당 시연을 조정한다.

발표 흐름: **공모전 발견 → 작년 참가 후기 확인 → 팀 모집 작성 → 다른 계정으로 참여 요청 → 팀장 수락 → 팀원 등록 확인**. 공고 출처와 마지막 확인 시각도 보여준다. 실제 수집기 실행은 필수 발표 항목이 아니다.

실제 후기/예시 폴백은 [후기 데이터 규칙](features/reviews.md), 공고 준비는 [공고 명세](features/opportunities.md)를 따른다. 검증 결과는 이 문서의 검증 항목에 실행 방법과 관찰 결과로 기록하며 실패·미검증을 통과로 표시하지 않는다.

## 배포 흐름

- Git 저장소를 초기화하고 의존성 버전·lockfile, DB 마이그레이션·seed를 함께 관리한다. 현재 계획만으로 저장소나 배포가 준비되었다고 간주하지 않는다.
- 로컬·Vercel에 Supabase URL, 공개용 키, 서버 전용 service-role 키를 구분해 설정한다. 서버 키에는 `NEXT_PUBLIC_` 접두사를 붙이지 않고 `.env` 파일은 커밋하지 않는다.
- DB 마이그레이션·권한 검사·검증된 seed 적용은 앱 배포와 별도 단계다. Git push만으로 DB가 갱신된다고 가정하지 않는다. 실제 사용자 데이터가 있는 DB에 초기화용 seed/reset을 실행하지 않는다.
- 최종 공개 전 타입 검사·프로덕션 빌드와 위 권한/트랜잭션 검증을 수행하고, 배포 URL에서 로그인·직접 상세 접근·모바일 핵심 흐름을 재확인한다. 테스트 실행 명령은 구현 시 추가한다.

```text
GitHub 저장소에 push
        ↓
Vercel이 자동 build/deploy
        ↓
공개 URL (*.vercel.app)
        ↓
Next.js가 Supabase에서 공고·후기·팀·저장 데이터 조회
```
