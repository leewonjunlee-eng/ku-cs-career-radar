# 경험 후기

[프로젝트 소개](../../README.md) · [구현 순서](../implementation-plan.md) · [공통 설계](../architecture.md)

> 구현 전 명세다. 아래 규칙과 완료 기준은 현재 구현·테스트 통과를 의미하지 않는다. 공통 인증·보안은 공통 설계를 따른다.

## 1. 목적과 MVP 범위

공고가 바뀌어도 같은 대상의 경험을 누적해 지원 판단을 돕는다. 유형별 선택 입력·익명 처리·본인 수정/삭제를 유지하며 사용자 임의 대상 생성·병합은 후속 범위다.

## 2. 사용자 흐름·화면

- 공고 상세, 연구실/인턴 정보, 기업 채용 정보에 `후기 보기`와 `후기 작성`을 연결
- 후기 카드에는 경험 시기, 참여 유형, 역할, 결과, 준비 기간, 사용 기술, 익명 여부를 표시
- 제목, 경험 시기, 본문과 연결 대상을 필수로 받고, 유형별 추가 항목은 선택 입력
- `좋았던 점`, `어려웠던 점`, `준비 팁`, `다시 한다면`은 작성 안내로 제공하며 모두 입력하도록 강제하지 않음
- 특정 개인의 개인정보, 회사/연구실의 비공개 정보, 근거 없는 비방은 작성하지 않도록 가이드 제공
- 공개 서비스에 문의 경로를 표시하고 개인정보 노출·부적절 게시물은 개발자가 확인 후 관리 도구로 삭제. 앱 내 신고 처리 화면은 후속 범위

| 유형 | 선택 입력 항목 |
| --- | --- |
| 공모전·해커톤 | 팀 규모, 담당 역할, 준비 기간, 결과, 다음 참가자를 위한 팁 |
| 학부연구생 | 연구 분야, 시작 당시 경험, 실제 업무, 주당 참여 시간 |
| 인턴 | 직무, 선발 과정, 실제 업무, 배운 점 |
| 취업 | 지원 당시 프로젝트·경력·학점 등 선택 정보, 전형별 경험, 합격 여부 |
| 대외활동 | 활동 국가/지역, 활동 기간, 선발 과정 |

취업 후기는 개인의 지원 당시 경험이며 합격 기준이나 합격 보장으로 표현하지 않는다. 후기 모아보기에서 대상, 유형, 경험 연도로 탐색할 수 있게 한다.

아래 내용은 실제 이용자 후기가 아닌 **가상 예시**다. 데모에 사용하면 카드와 상세에 `예시 후기`를 표시하고, 실제 후기와 통계에 섞지 않는다.

> 2025년 공모전 참가 / 백엔드 역할 / 4인 팀. 기획 검증보다 데모 완성도가 중요했고, 첫날에 API 명세를 정한 것이 도움이 됐다.

> 학부연구생 경험 / AI 연구실 / 6개월. 논문을 읽는 습관과 Python 실험 재현 능력이 특히 중요했다. 면담 때 관심 논문을 한 편 골라 질문을 준비했다.

> 가상 기업 신입 지원 경험 / 백엔드 직무. 프로젝트를 많이 나열하기보다 맡은 문제, 지표 변화, 기술적 의사결정을 구체적으로 설명한 포트폴리오가 도움이 됐다.

내 활동에서 본인의 후기를 조회하고 수정·삭제한다.

## 3. 관련 데이터 모델

<a id="대상-모델"></a>

### subjects (후기가 쌓이는 대상)

| 컬럼 | 설명 |
| --- | --- |
| id | 대상 ID |
| kind | 공모전 시리즈, 기업, 연구실, 프로그램 등 |
| name | 대상 이름 |
| official_url | 공식 홈페이지 (선택) |

예: `A 공모전`은 subject 하나이며 `2025 A 공모전 모집`, `2026 A 공모전 모집`은 별도 opportunities다. 후기는 subject에 연결하고 참여 회차는 선택 연결하여 올해 공고에서도 작년 후기를 찾을 수 있게 한다. 회사 인턴·취업 후기는 유형과 직무로 구분한다. 기존의 `target_type + target_id` 대신 실제 외래 키를 사용한다.

`subjects`는 유지한다. 작년 후기 조회가 발표 핵심이며, 모집 공고가 없는 기업·연구실 후기에도 공통 대상이 필요하다. 문자열 `series_key`로 대체하지 않는다. 회차 일치 검증은 `opportunities(id, subject_id)`의 UNIQUE와 `reviews(opportunity_id, subject_id)`의 복합 외래 키로 처리한다. `opportunity_id`는 선택이지만 `subject_id`는 항상 필수이며 `subjects(id)` 단일 외래 키도 별도로 둔다.

대상은 개발자가 seed/관리 스크립트로 미리 등록한다. 사용자는 작성 폼에서 기존 대상을 선택하며, 공고 상세에서 작성하면 대상과 회차를 미리 채운다. MVP에서는 사용자 임의 대상 생성·대상 병합을 제공하지 않는다.

### reviews

| 컬럼 | 설명 |
| --- | --- |
| id | 후기 ID |
| author_id | 작성자 사용자 ID |
| subject_id | 후기 대상 ID (subjects 외래 키, 필수) |
| opportunity_id | 실제 참여한 회차·공고 ID (선택, 동일 subject인지 검증) |
| review_type | 공모전, 학부연구, 인턴, 취업 등 |
| title | 후기 제목 |
| body | 경험 본문 (필수) |
| experience_year | 경험 연도 (필수) |
| period | 구체적인 경험 기간 (선택) |
| role | 역할 또는 지원 직무 |
| result | 수상, 합격, 참여 완료 등 결과 (선택) |
| preparation | 준비 과정 및 기간 |
| pros | 좋았던 점 |
| challenges | 어려웠던 점 |
| tips | 후배에게 줄 팁 |
| skills | 사용 기술 배열 |
| details | 팀 규모, 주당 시간, 프로젝트 등 유형별 선택 정보 (검증된 JSONB) |
| is_anonymous | 익명 공개 여부 |
| is_demo | 가상 예시 여부 |
| created_at | 작성 시각 |

역할, 결과, 준비 과정, 장단점과 팁은 선택이다. 익명 후기 작성자 ID는 공개 조회 응답에서 제외한다.

일반 사용자 작성은 서버에서 `is_demo=false`로 고정하며, 가상 예시는 개발자 seed만 생성한다. 예시 후기는 일반 목록·관련 후기·후기 수에서 기본 제외하고, 별도 `예시 보기`에서 카드·상세 모두 표시한다. 예시를 실제 경험자 후기나 참여 검증 완료로 표현하지 않는다. 익명 설정은 표시 정보만 숨기며 본문에 스스로 입력한 신원까지 자동 익명화하지 않는다고 안내한다.

`예시 보기` 토글은 후기 모아보기와 공고 상세의 관련 후기 양쪽에 제공한다. 예시 모드에서도 대상·경험 연도 필터와 `예시 후기` 표시는 유지한다.

## 4. 초기 후기와 발표 데이터

- 같은 subject의 올해 공고와 `experience_year`가 작년인 후기를 준비한다. 작년 원문을 확보한 경우에만 과거 opportunity를 등록·연결하고, 없으면 후기의 `opportunity_id=NULL`로 둔다. 과거 원문 URL을 만들어내지 않는다.
- 실제 경험 후기는 경험자의 동의하에 본인 계정으로 작성한다. 실제 후기를 확보하지 못했다면 `예시 보기`를 켜고 `예시 후기`라고 명시하여 누적 조회 동작만 시연한다. 허위 실제 후기 확보를 완료 조건으로 삼지 않는다.

## 5. 완료 기준·테스트

- 올해 공고에서 동일 대상의 작년 후기를 볼 수 있다.
- 작성·수정·삭제 결과가 재조회에 반영되며 새로고침 후에도 저장한 후기가 유지된다.
- 다른 사용자의 후기 수정·삭제는 거부된다.
- 잘못된 subject/회차 조합과 존재하지 않는 대상의 후기 저장은 거부된다.
- 익명 작성자 ID는 비로그인과 로그인 공개 응답 모두에서 노출되지 않는다.
- 일반 사용자는 `is_demo`를 변경할 수 없으며 기본 조회·집계에서는 예시가 제외된다. 예시 보기의 카드·상세 배지는 유지된다.
- 원본 테이블·뷰 직접 접근 차단은 [공통 보안 검증](../architecture.md#공통-출시-검증)에 포함한다.

## 6. 후속 확장

공감·앱 내 신고·참여 검증·유용한 후기 우선 노출은 [확장 아이디어](../../README.md#확장-아이디어)로 관리한다. 문의를 통한 최소 운영 대응은 MVP에서 유지한다.
