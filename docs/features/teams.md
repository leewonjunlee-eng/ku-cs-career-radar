# 팀 모집과 참여

[프로젝트 소개](../../README.md) · [구현 순서](../implementation-plan.md) · [공통 설계](../architecture.md)

> 구현 전 명세다. 아래 규칙과 완료 기준은 현재 구현·테스트 통과를 의미하지 않는다. 공통 인증·보안은 공통 설계를 따른다.

## 1. 목적과 MVP 범위

공모전·해커톤 공고에서 팀을 만들고 요청·수락을 통해 참가자를 모집한다. 수동 모집 종료도 유지한다. 실시간 채팅·일정 관리·자동 매칭은 후속 범위다.

## 2. 사용자 흐름·화면

- 특정 공모전·해커톤 공고에 연결된 팀원 모집 게시글 목록
- 모집 인원, 필요한 역할(프론트엔드/백엔드/디자인/기획), 기술 스택, 한 줄 소개 표시
- `팀 만들기` 또는 `참여 요청` 버튼
- `참여 요청 → 팀장 수락 → 팀원 등록 → 정원 도달 시 모집 종료`를 실제 구현
- 팀 생성 시 팀장도 팀원으로 등록하며 최대 인원에는 팀장을 포함
- 요청 취소·거절 상태를 제공하고 중복 요청과 정원 초과 수락을 방지
- 팀 연락 링크는 팀장과 수락된 팀원에게만 제공. 실시간 채팅은 후속 기능

내 활동에서 내가 만든 팀·참여 요청한 팀과 팀장이 받은 요청을 확인한다.

## 3. 관련 데이터 모델·기능 규칙

### teams

| 컬럼 | 설명 |
| --- | --- |
| id | 팀 ID |
| opportunity_id | 연결된 공모전 또는 해커톤 공고 ID |
| owner_id | 팀장 사용자 ID |
| name | 팀 이름 |
| introduction | 팀 소개 및 목표 |
| max_members | 최대 인원 |
| roles | 모집 역할 배열 |
| skills | 원하는 기술 스택 배열 |
| status | 모집 중, 모집 완료 |
| created_at | 생성 시각 |

한 팀당 모집글 하나로 시작하여 별도 team_recruitments 테이블은 두지 않는다. 연락 링크는 공개 팀 정보와 분리된 비공개 데이터로 보관하고 팀장·팀원만 조회한다.

- 팀 생성은 `create_team` DB 함수에서 팀 행·팀장 멤버 행·연락 정보를 한 트랜잭션으로 저장한다. 팀장 포함 `max_members >= 2`인 정수만 허용한다. MVP에서는 팀장·연결 공고·정원을 생성 후 바꾸지 않으며, 팀장과 `role=팀장`인 멤버가 일치하도록 생성 경로를 제한한다.
- 공모전·해커톤만 팀 생성·요청·수락이 가능하다. 확정 마감 이후에는 세 작업을 거부한다. 상시·미정은 원문 확인 안내와 함께 허용하되 실제 대회 접수 가능 여부는 보장하지 않는다.
- `status`는 팀 모집 자체의 상태다. 팀장이 수동으로 모집을 종료할 수 있고 정원 도달 시 자동 종료한다. 공개 화면의 `모집 중` 표시·팀 수는 팀 상태와 공고의 확정 마감 여부를 함께 반영한다.
- 모집 종료나 공고 마감 후에도 기존 팀원의 연락 조회 및 대기 요청의 취소·거절은 가능하다. 남은 대기 요청은 자동 거절하지 않고 `모집 마감` 안내와 함께 유지한다. 신규 요청·수락은 불가하다. MVP에서는 모집 재개, 팀 탈퇴·추방·삭제·팀장 양도를 제공하지 않는다.

### team_contacts (비공개)

| 컬럼 | 설명 |
| --- | --- |
| team_id | 팀 ID, 기본 키 및 teams 외래 키 |
| contact_link | 팀 연락 링크 |

공개 뷰에 조인하지 않는다. 조회는 서버에서 팀장·팀원 여부 확인 후, 수정은 팀장 확인 후 허용한다.

### team_members

| 컬럼 | 설명 |
| --- | --- |
| team_id | 팀 ID |
| user_id | 팀원 ID |
| role | 팀장 또는 팀원 |
| joined_at | 가입 시각 |

`(team_id, user_id)`는 유일하다. 현재 인원은 이 테이블로 계산한다.

### team_requests

| 컬럼 | 설명 |
| --- | --- |
| id | 참여 요청 ID |
| team_id | 지원한 팀 ID |
| user_id | 지원자 ID |
| message | 짧은 자기소개 |
| status | 대기, 수락, 거절, 취소 |
| created_at | 요청 시각 |

`(team_id, user_id)`는 유일하게 유지한다. 수락은 DB 함수 하나로 처리한다. 해당 팀 행에 `FOR UPDATE` 잠금을 건 뒤 팀장 권한, 대기 요청, 현재 인원과 정원을 확인하고 요청 상태 변경·팀원 추가·정원 도달 시 모집 마감을 한 트랜잭션에서 처리한다. 실패하면 전체 롤백하며 이미 수락한 요청은 중복 가입시키지 않는다. 팀원 등록은 이 경로와 팀 생성 경로로 제한한다.

- 요청 생성 시 본인 ID를 서버에서 넣고 팀장·기존 팀원의 지원, 모집 종료·확정 마감 팀의 지원을 거부한다. `대기 → 수락/거절/취소`만 허용하고 수락·거절은 팀장, 취소는 요청자만 수행한다.
- MVP에서는 거절·취소 후 같은 팀에 재요청하지 못하며 UI에도 안내한다. 이미 처리된 요청의 반복 수락은 추가 멤버를 만들지 않고 상태 충돌로 응답한다.
- 요청 생성·수락·거절·취소·모집 종료는 각각 서버 전용 DB 함수로 처리하며, 모두 동일한 팀 행을 먼저 잠그고 필요한 요청 행을 다음에 잠근다. 함수 내부에서 작업별 권한·현재 상태를 재검증하고, 요청 생성·수락에는 정원·공고 마감 검사도 적용하여 동시 수락뿐 아니라 수락과 취소/종료의 경쟁도 직렬화한다. 공고 마감은 잠금 획득 후 실제 작업 시점의 DB 시각(`clock_timestamp()`)으로 확인한다. 거절·취소는 모집 종료·정원 도달·공고 마감 후에도 대기 요청에 대해 허용한다.

이 최소 잠금은 유지한다. UNIQUE는 동일 사용자의 중복만 막으며, 다른 두 사용자의 요청을 동시에 수락할 때 정원 초과를 막지 못한다. 일반 인원 확인만으로 완료 기준을 충족한다고 문서화하지 않는다. 별도 큐나 복잡한 분산 잠금은 만들지 않는다.

## 4. 접근 권한

공개 응답·연락 조회·RPC 실행 권한의 단일 기준은 [공통 설계](../architecture.md)다. 팀장은 모집 정보와 연락 링크를 수정할 수 있지만 생성 후 팀장·연결 공고·정원은 변경할 수 없다.

## 5. 완료 기준·테스트

- 두 발표 계정으로 요청·수락·팀원 등록·수락 전후 연락 조회 권한을 확인하고, 새로고침 후 상태가 유지된다.
- 별도 통합 테스트에서 잔여 정원 1인 팀에 서로 다른 두 지원자의 대기 요청을 만들고 수락을 동시에 호출한다. 한 건만 성공하고 현재 인원·요청 상태·팀 모집 종료가 일치해야 한다. 동일 요청의 반복 수락도 멤버를 중복 생성하지 않는다.
- 수락과 취소/모집 종료를 동시에 실행해 먼저 직렬화된 작업에 맞는 일관된 최종 상태를 확인한다. 거절·취소 후 재요청, 팀장·기존 팀원의 지원, 마감 후 생성·요청·수락은 거부된다.
- 팀 생성 도중 강제 실패 시 팀·팀장 멤버·연락 정보가 일부만 남지 않는다.
- 다른 팀의 요청 수락과 비회원의 연락 조회는 거부된다. 공개 응답에는 팀 연락 링크가 노출되지 않는다.
- 팀과 참여 요청은 새로고침 후 유지되며 팀장의 모집 정보·연락 링크 변경은 재조회에 반영된다.
- 단일 트랜잭션 선언만으로 성공을 간주하지 않고 별도 테스트 DB에서 실패·경쟁 상황을 실제로 실행한다.

## 6. 후속 확장

팀 탈퇴·추방·삭제·팀장 양도·모집 재개는 MVP에 제공하지 않는다. 일정 관리·팀원 추천 등 제품 확장은 [README](../../README.md#확장-아이디어)를 따른다.
