# 공고 탐색·저장

[프로젝트 소개](../../README.md) · [구현 순서](../implementation-plan.md) · [공통 설계](../architecture.md)

> 구현 전 명세다. 아래 규칙과 완료 기준은 현재 구현·테스트 통과를 의미하지 않는다. 공통 인증·보안은 공통 설계를 따른다.

## 1. 목적과 MVP 범위

실제 커리어 공고를 탐색하고 저장한다. 검색·태그·마감 필터·이번 주 마감·마감 공고 포함은 필수이며, 자동 수집은 추가 목표다. 공고 상세의 후기와 팀 모집은 [후기](reviews.md)·[팀](teams.md) 명세를 따른다.

## 2. 사용자 흐름·화면

### 홈

- 상단: 서비스 소개, 검색창, `이번 주 마감` 카드
- 주요 메뉴: `기회 탐색 / 후기 모아보기 / 내 활동`
- 필터: 카테고리, 관심 분야 태그, 마감 임박 여부
- 본문: 공고 카드 목록

### 공고 상세

- 공고 정보, 관련 후기, 팀 모집을 한 페이지의 탭 또는 섹션으로 제공
- 공모전은 동일 대회의 과거 연도 후기를 함께 노출하고 경험 연도와 회차를 명시
- 기업·연구실도 공고가 마감되거나 새 공고가 생겨도 기존 후기를 이어서 조회
- 원문 링크와 마지막 확인 시각 표시

### 공고 카드

- 제목, 기관/회사, 카테고리, 태그
- 원문이 고려대 웹사이트에 있는 공고는 `고려대` 배지 표시(상세 화면도 동일). 추후 고려대 출처만 따로 보는 필터의 기준이 된다
- 마감일 및 D-day
- 원본 공고로 이동하는 링크
- 북마크 버튼
- 공모전·해커톤인 경우 `팀원 찾기` 버튼과 현재 모집 중인 팀 수 표시

북마크는 로그인 후 저장·취소하며 내 활동에서 다시 조회한다.

## 3. 데이터 모델과 기능 규칙

### opportunities

| 컬럼 | 설명 |
| --- | --- |
| id | 공고 ID |
| subject_id | 후기를 함께 조회할 대상 ID (subjects 외래 키) |
| title | 공고 제목 |
| organization | 주최 기관 또는 회사 |
| category | 인턴, 채용, 해커톤, 공모전, 연구실, 대외활동 등 |
| tags | 분야 태그 배열 |
| deadline | 마감 시각 (선택, 한국 시간 기준 표시) |
| deadline_type | 확정, 상시, 미정. 미정 날짜를 임의로 추정하지 않음 |
| deadline_precision | 시각 또는 날짜. 상시·미정은 NULL |
| source_name | 출처 이름 |
| source_url | 원본 공고 링크 |
| is_korea_university_source | 원문이 고려대 웹사이트(`korea.ac.kr` 및 하위 도메인)에 있는지. `source_url`에서 DB가 자동 계산하며 직접 입력하지 않는다 |
| ingestion_method | 수동 입력 또는 스크립트 수집 |
| description | 짧은 설명 |
| created_at | 등록 시각 |
| last_checked_at | 원문 확인에 성공한 마지막 시각 |
| updated_at | 공고 정보 수정 시각 |

원문 URL을 정규화하고 `source_url NOT NULL UNIQUE` 및 upsert로 동일 원문의 중복 저장을 막는다. 서로 다른 출처에 실린 같은 행사까지 자동으로 합치는 것은 후속 범위다.

`opportunities.status`는 저장하지 않는다. 확정 마감은 DB 조회 시 `deadline <= now()`이면 마감으로 계산한다. `deadline_type=확정`이면 deadline이 필수이며 상시·미정은 NULL을 사용한다. 상시·미정은 각각 그대로 표시하며 모집 중이라고 단정하지 않는다. 별도 마감 갱신 Cron은 필요 없다. 기본 목록에서 확정 마감 공고는 숨기되 상세·후기는 유지하고, 브라우저에서도 마감 시각이 지나면 표시를 갱신한다. 조기 종료는 원문 재확인 후 마감 정보를 수정한다.

- `deadline`은 `timestamptz`로 저장하고 화면·D-day는 `Asia/Seoul` 기준으로 계산한다. 원문에 날짜만 있으면 해당 날짜 다음 날 00:00 KST를 배타적 마감 시각으로 사용하고 `시간 미제공·날짜 기준`임을 표시한다. 이를 구분할 `deadline_precision`(시각/날짜, 상시·미정은 NULL)을 둔다. 원문이 시간대를 지정하면 그 기준으로 변환한다.
- D-day는 남은 24시간 단위가 아니라 KST 달력 날짜 차이다. 날짜 기준 공고는 원문의 마감 날짜를 사용한다. 당일 아직 마감 전이면 `D-day`, 시각이 지나면 `마감`으로 표시한다.
- 마감순은 미마감 확정 공고를 먼저 오름차순 정렬하고 상시·미정을 뒤에 둔다. 동률은 `id`로 정렬한다. `이번 주 마감`은 KST 월요일 00:00부터 다음 월요일 00:00 전까지의 마감 날짜 중 미마감 확정 공고만 포함한다.
- 마감된 공고 포함 필터를 제공하고, 저장 목록·상세에서는 마감 공고도 유지한다. 확정 마감과 NULL 조건은 DB CHECK로 검증한다.
- MVP 검색은 제목·기관·설명의 `ILIKE` 부분 일치를 사용한다. 입력은 매개변수로 전달하고 `%`, `_`는 검색어의 문자로 처리한다. 카테고리·태그·마감 필터와 함께 적용하며 전문 검색 엔진이나 한국어 형태소 검색은 후속 범위다.

### bookmarks

| 컬럼 | 설명 |
| --- | --- |
| user_id | 사용자 ID |
| opportunity_id | 저장한 공고 ID |
| created_at | 저장 시각 |

`(user_id, opportunity_id)`를 유일하게 유지해 중복 저장을 방지한다.

공고의 `subject_id`는 [후기 대상 모델](reviews.md#대상-모델)을 참조한다. 공통 외래 키·삭제 정책은 공통 설계에서 관리한다.

## 4. 실제 데이터와 수집

아래 [후보 출처 목록](#후보-출처-목록)에서 공개 열람과 페이지 구조를 짧게 확인하여 첫 수집 대상 1곳을 선정한다. 이 가능성 확인은 UI 구현 후반까지 미루지 않는다. 수집 대상이 정해지지 않아도 UI·DB 구현은 진행하고, 수집기 구현은 추가 목표로 둔다. 필수 데이터는 원문을 확인한 실제 공고를 수동 입력해 확보한다.

| 확인할 정보 | 목적 |
| --- | --- |
| 사이트 이름과 게시판 URL | 수집 범위 특정 |
| 얻고 싶은 정보 | 공모전, 연구실, 인턴·채용 등 분류 |
| 공개 열람 여부 | 로그인 없이 접근 가능한 출처 우선 선정 |
| RSS/API 또는 페이지 구조 | 출처에 맞는 수집 방식 결정 |

- 가능하면 게시판 목록 URL과 대표 공고 상세 URL을 함께 받는다.
- 실제 자동 수집 가능 여부와 공개된 수집 조건은 출처를 확인한 뒤 판단한다.
- 수집 시 제목, 대상, 요약, 원문 URL, 마감 정보, 확인 시각을 정규화하고 같은 원문은 갱신한다.
- 출처의 게시일을 마지막 확인 시각으로 대신 쓰지 않는다. 수동 입력과 스크립트 수집 여부도 기록한다.
- 실패나 빈 응답으로 기존 공고를 일괄 삭제하지 않는다. 성공한 공고의 확인 시각만 갱신한다.
- 초기에는 개발자가 실행하는 스크립트로 실제 수집을 검증하고, 주기 실행은 이후 연결한다. 수동 실행을 자동 갱신 중이라고 표시하지 않는다.
- 공고 수집과 사용자 후기 작성은 분리한다. 외부 후기를 실제 사용자 작성 후기처럼 가져오지 않는다.

#### 선정 규칙

- 로그인·403으로 막힌 출처(에브리타임, 고파스)는 기술적으로 접근이 안 되므로 수집 대상이 아니다. 사용자가 직접 확인하는 참고 링크로만 둔다.
- `약관 확인 필요` 출처도 후보 목록에 그대로 포함한다. 비영리 해커톤 프로젝트이므로 출처를 미리 좁히지 않는다.
- 첫 수집 대상 1곳은 **공개 열람 + 구조가 단순**한 곳에서 고른다. 현재로는 고려대 교내 출처(정보대학·AI 중심대학·SCC)와 DACON이 후보다.
- 나머지는 원문을 확인한 뒤 수동 입력으로 확보한다. 출처 상태가 바뀌면 이 표의 메모를 갱신한다.

**추후 확인 항목**: LinkedIn Jobs, 잡코리아, 사람인, 원티드, 로켓펀치, 점핏, 캠퍼스픽, Linkareer, Wevity의 `robots.txt`·이용약관. 기능을 전부 만든 뒤에 확인한다.

### 초기 콘텐츠

- 우선순위 3에서 공모전·해커톤, 학부연구, 인턴·취업의 초기 집중 분야를 실제 공고로 채우고, 발표일에도 마감 전인 공모전·해커톤을 확인한다. 원문의 마감일을 데모 편의로 바꾸지 않는다.
- 2026-09-18 준비분: `content/initial-content.json`(대상 16, 공고 17, 예시 후기 템플릿 3), 원문 인용·확인 시각·실패 기록은 `content/source-evidence.md`. DB 입력은 스키마 검토 후 3단계에서 한다.
- 확인 시점 기준 열린 공모전·해커톤은 `2026 한국관광 데이터랩 활용 경진대회`(2026-09-30 14:00 KST) 1건뿐이다. 발표가 그 이후면 열린 공모전 데모 공고가 없으므로 발표 직전 새 공고를 원문 확인해 추가해야 한다.
- 한국관광 데이터랩은 페이지에 무단 수집 금지 문구가 있어 자동 수집 후보에서 제외한다.

## 5. 완료 기준·테스트

- 원문을 확인한 실제 공고가 DB에 저장되어 있고 출처·원문 링크·확인 시각을 볼 수 있다.
- 검색·태그·카테고리 조합과 마감순 정렬을 확인한다. KST 당일·자정·주 경계, 날짜만 있는 마감, 상시·미정 데이터를 검증하고 마감 후 기본 목록 제외·상세/저장 목록 유지가 일치해야 한다.
- 동일 공고의 북마크 반복 저장은 중복되지 않고 취소 후 목록에서 사라진다. 타인의 저장 목록에 접근할 수 없다.
- 직접 상세 URL 접근과 저장 목록에서 마감 공고 조회가 가능하다.

## 6. 후속 확장

수집기를 구현한 경우 추가 완료 기준은 **1회 실행 결과 저장·조회, 반복 실행 시 중복 방지, 실패·빈 응답 시 기존 데이터 보존**이다. 이 검증 전에는 수집기 완료로 표시하지 않으며, 수집기를 후속으로 미루는 것은 전체 필수 MVP 완료를 막지 않는다. UNIQUE + upsert 외에도 URL 정규화와 파싱은 출처별 작업이 필요하다.

수집기 우선순위는 [구현 순서](../implementation-plan.md), 방학·학기별 준비 안내를 포함한 제품 확장은 [README](../../README.md#확장-아이디어)에서 관리한다.
